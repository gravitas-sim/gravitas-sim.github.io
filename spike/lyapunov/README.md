# Lyapunov cloud spike — Worker feasibility evidence

**This is not production code. It is not deployed, it is not linked from the
site, and nothing in `js/` imports it.** It is kept in the repository because it
is the evidence behind a decision.

> The decision itself is in [`MULTI_WORLD_DECISION.md`](../../MULTI_WORLD_DECISION.md)
> at the repository root. Read that first. This file only says how to re-run the
> measurements.

`tests/spikeNotShipped.test.js` asserts that `build.js` never names this
directory and that the committed service-worker manifest does not offer it to
anyone.

## What is here

| File                     | What it does                                                                            |
| ------------------------ | --------------------------------------------------------------------------------------- |
| `index.html`             | the fifty-member Lyapunov ensemble, in a pool of Workers                                |
| `cloud.worker.js`        | one worker: restores a three-body system, perturbs it, integrates, returns trajectories |
| `scenario-probe.html`    | builds four catalog scenarios in four concurrent Workers                                |
| `scenario.worker.js`     | one worker: `buildWorld()` with an injected context and no interface                    |
| `import-probe.html`      | imports each engine module in its own Worker and reports which evaluate                 |
| `import-probe.worker.js` | the one-module-per-worker probe                                                         |
| `targets.json`           | the module list the import probe walks, generated by the command below                  |

## Running it

Serve the repository root over HTTP — module Workers will not load from
`file://` — and open the pages. Any static server will do:

```
npx http-server . -p 8015 -c-1
```

- `http://localhost:8015/spike/lyapunov/index.html` — the ensemble.
  Query parameters `?steps=12000&sample=40` tune it; those are the defaults and
  are what the recorded numbers used.
- `http://localhost:8015/spike/lyapunov/scenario-probe.html` — four scenarios in
  four Workers.
- `http://localhost:8015/spike/lyapunov/import-probe.html` — which modules load
  in a Worker realm.

Each page leaves its result on `window.__cloud`, `window.__scen` or
`window.__probe` so it can be read from a console or a driver.

To regenerate `targets.json` after `js/physics.js`'s imports change:

```
node -e "const fs=require('fs');const raw=fs.readFileSync('js/physics.js','utf8');const specs=[...raw.matchAll(/(?:^|\n)\s*import\s+(?:[\s\S]*?from\s*)?['\"]([^'\"]+)['\"]/g)].map(m=>m[1]);fs.writeFileSync('spike/lyapunov/targets.json',JSON.stringify([...new Set(specs.filter(s=>s.startsWith('.')))].map(s=>'/js/'+s.replace(/^\.\//,''))))"
```

Wall times are machine-dependent and will not reproduce exactly. The two things
that should reproduce are the **shape** — separation growing by four to five
orders of magnitude from a 10⁻⁶ perturbation — and the **ids starting from zero
in every worker**, which is what says each realm has its own module instance.

## Things that will trip you up

- **Cost is dominated by close encounters, not by step count.** The Pythagorean
  problem has near-collisions and the integrator substeps through them, so 10×
  the steps costs far more than 10× the time. That is the physics.
- **Do not plot the trajectories.** One body is ejected and its coordinate runs
  away, so any spatial window that holds the ejection collapses everything else
  to a point. The separation on a log axis is the readable artifact and the
  honest one.
- **A module that throws during evaluation is remembered as broken.** Fixing the
  source and reloading is not always enough — the module map can keep serving
  the failed record for that URL. If a page insists a module is broken after you
  have fixed it, serve on a different port.
- **`js/ui.js` cannot load in a Worker** and is not expected to. The workers use
  `buildWorld()` directly with an injected context.

## Where the shipped regression tests are

This spike does not run in CI. The properties it established are held by:

- `tests/workerCompatibility.test.js` — the engine modules evaluate in a realm
  with no DOM, `buildWorld()` builds a real scenario there, and the reset event
  still fires when a window does exist
- `e2e/workerRealm.spec.js` — a real browser Worker builds a real scenario
- `tests/spikeNotShipped.test.js` — this directory is not deployed
