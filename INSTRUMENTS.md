# The instrument library

A few real facilities, every value cited, and a typical entry labelled as such
(Roadmap III, Prompt 209). Every observing calculation needs a telescope, an
instrument, a detector and a site with real parameters; without one shared,
cited table each lesson would invent its own. The library holds five facilities
with their values and the sources of each value. **A value the sources do not
state is absent: never estimated, never defaulted, never zero for unknown.**
Nothing a student sees changes with this prompt; it is the table the exposure
planner (210), the calibration lessons (211, 212), the spectrograph model (213)
and the strategy and survey prompts (214, 215) will read.

A facility is one telescope, its instruments and, on the ground, its site. Two
of the facilities are single units of an identical fleet (Las Cumbres
Observatory's 0.35 m and 1.0 m telescopes); the entry names the node whose
published site values it uses. The typical entry is for lessons that need no real
facility: its every value cites the project's own convention (the detector lab's
defaults, `DEFAULT_DETECTOR`), and a test holds the two equal so that the number
lives once.

## What a value is

Each number in `tools/instruments/*.json` is `{ "v", "u", "s" }` plus optional
`at`, `q` and `n`:

| Field | Meaning |
|---|---|
| `v` | a finite number, or `[low, high]` for a range the source states |
| `u` | a unit of `js/units/registry.js`, or registry units joined by `/`, with a whole power where needed (`m^2`, `arcsec/pix`, `electron/count`, `electron/s/pix`, `mag/arcsec2`); its dimension is the parameter's |
| `s` | the source id, in `sources.json` |
| `at` | where in the source (a table, a section) |
| `q` | a qualifier: `typical`, `upper`, `approx`, `assumed`, `estimated`, `inferred`, `median`, `effective`; the source's own word, never ours |
| `n` | a note: what the source says about the number, or what a reader must not assume |

A text value (a filter list) is `{ "t", "s" }`. A value is stored in the unit the
source uses; the adapters convert by registry factors and refuse a unit they do
not take. The registry gained three units for this: `electron`, `deg2` and
`airmass`.

Each source in `sources.json` has a kind, a title, authors, a year, a reference,
an https address (a typical source has none), a **retrieval date**, a **method**
and a **rights basis**.

## Rights and method (D-R10-209-01)

Every value is a bare numerical specification of a public instrument, stated in a
public paper or on the facility's public page, credited to it with the date it
was read. No text, table or figure of a source is reproduced; the one table that
is close to transcription, the Rubin per-band table (Ivezić et al. 2019, Table 2),
is six numbers in each of five rows and is credited as such. The basis is *facts
with attribution*, recorded as its own decision rather than inherited from
another source (roadmap rule 4); the licence of each arXiv paper was not read.
Every source was read through a summarising web fetch on 2026-10-28, not from the
typeset document, so a value is as that fetch reported it from the source. The
cross-checks below are the independent check on the transcription: a wrong digit
in a pixel size or a depth would not satisfy them.

## Cross-checks (the oracle)

`tools/instruments-validate.mjs` (`npm run instruments:validate`) recomputes a
cited value from other cited values; the bounds were committed in
`tests/fixtures/instruments/thresholds.json` before the table existed.

| Row | Relation | Bound |
|---|---|---|
| o1 | pixel scale = 206265 arcsec x pixel size / (f-ratio x aperture) | 5 percent |
| o2 | field = pixels x pixel scale (area, for a mosaic of sensors) | 10 percent |
| o3 | GBT collecting area = pi (D/2)^2 | 0.1 percent |
| o3b | GBT half-power beam between 1.0 and 1.4 lambda/D | stated |
| o4 | Rubin 5-sigma depth from C_m, the sky brightness and the seeing | 0.05 mag |
| o5 | a zero point implies a throughput between 0.10 and 1.00 (radiation kernel's `photonRate`) | stated |
| o6 | full well over gain fits a 16-bit converter | 10 percent |

A leg whose inputs are not all in the table is N/A and names the missing field,
never a pass; the tool prints the counts. **The two failures are kept failing and
labelled:** the Las Cumbres paper's zero points for u' (17.5) and zs (18.4) imply
system throughputs of 2 and 5 percent, under the 10 percent floor, where the
other three bands imply 59, 46 and 22 percent. Either those two filter and sensor
combinations are that poor, or the paper's wording ("in units of log(e-/s)") hides
a convention this table does not know; the values stay as published, the legs
stay failing, and `tests/instrumentLibrary.test.js` lists them by name so that
neither a fix nor a new failure goes unnoticed.

The Rubin depth leg also settled a reading: the footnotes as extracted label the
rows of seeing 0.92 to 0.76 arcsec "delivered median zenith seeing" and 0.81 to
0.68 "effective seeing", but the depth formula, which uses the effective seeing,
reproduces all six tabulated depths to 0.01 mag with the first row and misses by
0.13 mag with the second. The two labels may be exchanged in the extraction, so
only the first row is stored, under the footnote's label with the doubt in its
note. It should be checked against the typeset table.

## What is deliberately absent

- **Sinistro gain.** The page states gain only per readout mode (6.6 e-/ADU in
  the binned central mode, 1.0 after processing), not for the full frame.
- **Dark current** for the 0.35 m camera ("TBD" on the page), TESS and Rubin;
  **gain** for TESS and Rubin; **a zero point** for the 1.0 m, TESS and Rubin
  (Rubin's `throughputConstant` is a different quantity and is named so).
- **Obstruction** for the 1.0 m, TESS and Rubin (a secondary's diameter is stored
  where a source gives it, never an obstruction ratio).
- **Extinction** and **seeing by band** for the Las Cumbres sites (one median
  seeing and a V-band sky brightness, as tabulated).
- **GBT** gain in K/Jy and pointing accuracy.
- **Site coordinates are the published node's**, not a survey of the dome.
- TESS is the design of the 2015 paper (Phase B), not the flight camera.
- The GBT system temperature is the Observatory's 20 K; a 2011 paper reports
  18 K at the zenith for the same receiver (in the note).

## Adopters

The three consumers read the table through `js/instruments/`; no existing page
imports the table, so no bundle pays for it until a panel does.

| Consumer | Function | What it takes |
|---|---|---|
| The observing-window planner (`js/observingWindow.js`) | `observingNightAt(id, ...)` in `planner.js`; `siteOf(id)` in `index.js` | a facility's published latitude, longitude and elevation; identical to the planner called with the numbers by hand |
| The detector kernel (`js/kernels/detector/frame.js`) | `detectorOf(id)` in `detector.js` | gain, read noise, full well and dark current as the kernel takes them, with each value's source and qualifier, and the fields the table lacks listed (the kernel's own defaults fill those; the adapter never does) |
| The forward models (`js/forward/models/ccd.js`) | `imagerSetupOf(id, ...)` in `detector.js` | a `gravitas.observing-setup/1` imager block: array, pixel scale in arcsec and the seeing as the PSF, or an error naming what is missing |

A range is read at its low end, middle or high end by the caller's choice and
the choice is reported. A sensor over the kernel's million pixels needs a
cutout size passed in.

## A course's own telescope

`gravitas.instrument/1` (`sdk/schemas/instrument-1.schema.json`, `FORMATS.md`) is
the pack kind: one facility with its own sources and sites. It is held to the same
validator as the built-in table, and may not reuse a built-in id.
`npm run sdk -- init instrument-pack <id>` starts a typical entry with one value;
`validate` lists what is wrong by file and line; `test` runs the cross-checks.
Nothing in a running copy of Gravitas reads such a pack yet.

## Adding a facility

1. Add the sources to `tools/instruments/sources.json` (title, reference, https
   address, retrieval date, method, rights basis); read the terms, and never
   circumvent a block.
2. Add `tools/instruments/<id>.json` (and a site to `sites.json` if it is new),
   each value with its unit, source and place in the source. Leave out what the
   source does not state.
3. `npm run instruments:data`, then `npm run instruments:validate` and
   `npm test -- tests/instrumentLibrary.test.js`. A failing cross-check is a
   finding about the table or the reading of its source: record it, do not widen
   the bound.
