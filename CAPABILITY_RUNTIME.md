# The capability runtime

The first production slice of [PLATFORM_PACKAGE_RFC.md](PLATFORM_PACKAGE_RFC.md)
(verdict B): three built-in capabilities are described by
`gravitas.capability-package/1` manifests and reach the application through
one runtime, and everything else stays where it was, as the core, until it is
migrated in its own slice. [docs/capabilities.md](docs/capabilities.md) lists
the installed packages; it is generated from them.

## What is packaged

| Package                             | Kind     | What it provides                                                                            | Reached through                                                    |
| ----------------------------------- | -------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `gravitas.power-law-instruments`    | built-in | the four power-law instruments, and the model they draw                                     | `LAZY_FAMILIES.powerLaw` in `js/widgets.js`, read from the catalog |
| `gravitas.sdss-dr18-spectra`        | built-in | four observed stellar spectra, with their provenance                                        | `spectraReady` in `js/stellarSpectraWidgets.js`                    |
| `gravitas.lesson.power-law-gravity` | built-in | _What If Gravity Were Not Inverse Square?_ and its Spanish shadow; requires the instruments | the lesson registry, whose loaders the runtime installs            |

Every public identifier is what it was: widget ids, the lesson id and its step
sids, the route, the progress key, the share-link format. Nothing a reader has
saved or linked to changes.

## How it works

- **Manifests** - `capabilities/*.json`, validated at build time by
  `npm run capabilities:check` (in CI's checks job): shape and declarative
  safety, dependencies and cycles, and that each claim is true of the
  repository - the code it names is in the reviewed builtin registry, its files
  exist and sit in the service-worker precache under the offline class it
  declares, its validation checks exist, and its licenses and citations are in
  `LICENSES.md` and `NOTICE`.
- **Catalog** - `js/platform/catalog.generated.js`, direct lookups generated by
  `npm run capabilities`: each package's version, platform range and
  requirements, each public id's builtin entry and owner, and any declared
  migrations. Titles, assets and licenses never ship.
- **Builtins** - `js/platform/builtins.js`, the reviewed list of modules a
  manifest may name, one literal `import()` each, and only for what the runtime
  loads by id: an entry for a module a family already imports would split it
  out of the family's chunk.
- **Runtime** - `js/platform/resolver.js`:
  `resolve()` orders a package after what it needs, checking the platform API
  and every range and refusing cycles; `loadBuiltin()` loads a module once for
  any number of callers and forgets a failure so the next ask fetches again;
  `providerOf()` names the package behind a public id, or `null` for the core;
  `migrateSavedProgress()` carries saved answers across a package's declared
  renames. Failures are `CapabilityError`s with a stable `code` (`unknown-package`,
  `api-range`, `requirement`, `cycle`, `unknown-builtin`, `load-failed`) and
  whether a retry can help.
- **Loading and failure, as a reader sees them** - unchanged, and now reached
  through the runtime: an instrument family's loading note is a status region,
  a failed one offers Try again or Reload; a lesson that cannot load says so in
  a toast (`inv.load.failed`); the spectra say they are loading or could not be
  loaded, in both languages, in the canvas and its readout.
- **Migrations** - a package declares renames of its own public ids, keyed on
  the versions they migrate from (`js/platform/migrate.js`). The lesson engine
  applies them to a packaged lesson's saved answers as it reads them, and
  `gravitas_capability_versions` records which version each was last read
  under. An unstamped save is a 1.0.0 save: a package's first version keeps the
  ids its content had before it was packaged.
- **Offline** - the service-worker generator takes each asset's class from its
  package (`core`, `optional`, `locale` for a translation warmed per language,
  `none`) and refuses a declaration it cannot honor; the platform's own modules
  are core entries.
- **Audits** - the scene audit (`tools/lesson-scene-audit.mjs`) says which
  readouts are observations by following imports, so it follows a
  `loadBuiltin('builtin:<id>')` through `js/platform/builtins.js` as it would
  the literal `import()` it replaced, and stops on an id it does not know. A
  slice that reaches data some other way has to teach it that way too:
  `audit:scene:check` is where the loss shows, and it runs in the release gate,
  not in CI.
- **The core** - an instrument family, lesson or dataset without a package is
  found where it always was. Moving one is a manifest, a builtin entry and a
  registry line; nothing about the others changes.

## One requirement deferred, and why

Prompt 09 asks the runtime for schema validation. Every package installed today
is built in and validated by the build, and the runtime accepts only the catalog
the build compiled, so a package it has not validated cannot reach it. The
validator itself (`checkAgainstInstalled()` in `js/platform/manifest.js`, with
its tests) is ready for the day a package can be imported, and arrives in the
browser with that feature: shipping it now costs 8.2 KB of a deferred budget
that has 2.1 KB to spare, which would mean raising the ceiling for code nothing
calls.

## Migration inventory

Packaged: 3 capabilities. Still in the core: 16 instrument families, 23
lessons, the GWOSC, GW150914 and MIST datasets, 59 scenarios. Every family,
packaged or not, has since been fetched on demand
([LAZY_CAPABILITIES.md](LAZY_CAPABILITIES.md)), so what is left here is
ownership, not loading.

The next families to migrate, in order, each its own slice with this one's
acceptance:

1. **The transit family and _Finding Planets by Their Shadows_** - already lazy,
   one lesson, no dataset: a manifest, a builtin entry, the family's
   `LAZY_FAMILIES` line read from the catalog.
2. **Both gravitational-wave families, with the GWOSC and GW150914 data
   packages and _Listening to Spacetime_** - the first package with two
   families and two datasets, and the one that needs `requires` between
   instrument and data packages.
3. **The MIST tracks, with _A Universe of Stars_ and _Lives of Stars_** - the
   dataset start-up shares (`js/lessonStage.js`), so it needs the start-up
   question settled first.
4. **The other families**, one lesson group at a time. Each is already a
   `LAZY_FAMILIES` entry; packaging one reads that entry from the catalog.
5. **Instructor guidance** split per lesson into each lesson's package.
6. **Scenarios last** - their id is the display name stored in share links, so
   they need a stable id and an alias map before a package can own one.

The deferred total is the constraint on this list: 4177.9 of 4180 KB. Moving a
family behind a lazy import saves bytes on every route but its own, not on the
total - Prompt 06 measured the total growing a little as families became chunks
of their own - so the next slice needs either savings found elsewhere or a
budget decision made on its own merits, not to fit it.

Savings were found: vendoring only the Chart.js Gravitas draws paid for moving
the last thirteen families on demand and left the deferred total at 4152.6 of
4180 KB (LAZY_CAPABILITIES.md). A family that is already lazy is expected to
cost its catalog entries and its builtin line when it is packaged, not another
chunk; that is to be measured when one is.
